## EGM method and convergence

The installed workflow is `/Users/davidai/.claude/plugins/cache/egm/egm/0.1.0/skills/egm-review/SKILL.md` and `egm-review-loop/SKILL.md`. Its stages are:

1. Initial zoom-out (`zoom_out`).
2. Comprehension (`comprehension`).
3. Feature critique (`design_critic`, `structural`, `style`).
4. Intermediate zoom-out (`zoom_out`).
5. Implementation readiness (`implementation_readiness`, `codebase_details`, `style`).

Every requested reviewer receives a recorded `completed` or `not run` status. A failed reviewer is retried once and otherwise marked `not run`; it is never counted as a zero-finding review. A clean round has every requested reviewer `completed` and no unsettled Blocker or Major finding. Nits do not block. Settled findings retain their contest/accepted-risk rationale; a later recurrence in a previously repaired scope reopens the finding.

Rounds 1–7 are design-stabilization reviews, not final convergence candidates; the user explicitly authorized continued audit and repair beyond the initial five-round exploratory window. A new final EGM run begins only after implementation on the final changed plan and evidence and has at most five rounds. Final acceptance requires two consecutive clean rounds within that new run. External unknowns document unavailable operator facts; they never waive a design, implementation or verification finding. Reaching the final-run cap without convergence, repeated churn or a `not run` required reviewer prevents an EGM success claim. Earlier stabilization rounds count neither toward nor against the final two clean rounds and are not themselves an EGM success or failure claim.

## Proposed target architecture

### Component ownership and data flow

* **React** renders public projections and the current viewer's authorized private projection. It never chooses cards, multipliers, bounty awards, pot allocations, insurance terms or house balances.
* **Node table/event coordinators** own hand timers, registration, negotiation, stage transitions and presentation barriers. Shared pot evaluation and settlement remain in the existing table/pots path; new workflows do not create parallel poker evaluators.
* **SQLite** is the durable authority for player/house balances, operation receipts, private active-play checkpoints and public history. A checkpoint contains private deck/cards, actor and deadlines, RIMT negotiation, Spin presentation acknowledgements, Battle stage/inventory and a schema/revision identity.
* **Browser presentation** receives only the fields required for its role. Pending RIMT projections exclude opposing hole cards, the private server-side `PokerTable` base-hand object (including the viewer's mutable copy; the viewer still receives their existing authorized hole-card projection), remaining deck, allocation plans and future boards. Battle public history excludes deck state, draw tickets, seat tokens, private traces and concealed folded cards.
* **TournamentRoomOwner** in `app/server/tournament-room-owner.js` supplies the existing ensure/restore/dispose ownership and scheduled settled-hand save patterns. Its existing snapshots are taken only at settled-hand boundaries; active Run It Multiple Times (RIMT), Spin and Battle use the finer-grained checkpoint above because a settled-hand snapshot cannot reconstruct pending choices or presentations.

### One unit-of-work boundary

Create `withGameTransaction` in the server data layer. It uses `BEGIN IMMEDIATE` on the existing SQLite connection and exposes the connection to ledger, game, house, audit, receipt and checkpoint writers. `addTransactionEx` and `settleSpinPayout` must accept that connection/transaction context and join the active outer transaction instead of opening a nested `BEGIN`; only the outermost owner commits or rolls back.

A settlement writes the hand/result, player and house movements, operation receipt, once-per-hand side effects and next checkpoint in one transaction. Any failed write rolls back all of them. Fault injection covers every write boundary and retries the committed operation without duplicate effects.

`game_checkpoints` stores `(room_id, kind, revision, operation_id, schema_version, engine_version, rules_json, status, state_json, reason, created_at, updated_at)` with `UNIQUE(room_id, kind, revision)` and a partial unique index permitting only one `active` row per room/kind. Valid transitions are `active → terminal` and `active → quarantined`; quarantine records a reason and audit identity and has no direct resume transition. Checkpoint reconstruction validates schema, immutable `rules_json`, `engine_version`, bankroll, cards, deadlines, allocations and linked receipts before activation. Restore uses the persisted rules snapshot and compatible engine-semantics version; differing rules or unsupported engine semantics quarantine the workflow instead of applying current code/rules. A valid active checkpoint resumes from its persisted revision. A corrupt or incompatible checkpoint is quarantined and only that workflow stays unavailable with an explicit recoverable error; the server never guesses replacement cards or payouts and never silently substitutes an earlier checkpoint. An authorized administrator may separately cancel the quarantined workflow through a new audited, exactly-once refund transaction.

`withGameTransaction` uses the existing single JavaScript thread and synchronous `DatabaseSync` connection; its strictly synchronous callback cannot use `await`, so no application-wide writer queue or generic clone-on-write framework is introduced. `BEGIN IMMEDIATE` protects the database, while per-aggregate expected revisions are checked immediately before staging and again after `BEGIN IMMEDIATE`. Only a coordinator whose new/modified workflow needs atomic in-memory installation supplies a synchronous capture/install changeset; commands touching several coordinators capture them in sorted room-ID order. Unrelated legacy coordinators are not cloned. Immediately after `BEGIN IMMEDIATE`, revalidate receipts, every affected account/room/house/config revision, balances and exposure from SQLite; a stale distinct operation then returns 409 before mutation. Before the single SQLite commit, run every covered persistence-bearing hook and write ledger/history/receipt plus any active workflow checkpoint. Only after all pre-commit work succeeds, commit. Then install the captured changesets and synchronously publish the committed events/replies in sequence order.

A pre-commit failure rolls back the database, discards captured changes and emits nothing. Rollback is never promised after commit. If any post-commit installer throws or a multi-coordinator install is incomplete, every affected coordinator immediately enters a fail-stop unavailable state and serves no further events/snapshots; it is rebuilt and validated from its committed recovery authority before reactivation. Ordinary cash instead completes the audited close/refund path. Exception-injection tests distinguish a caught install failure from a real process crash and cover multi-coordinator and ordinary-cash cases. Ordinary cash retains the existing close/crash-refund authority and never resumes an active private hand; tournaments retain their existing settled-hand snapshots. Every active new-workflow checkpoint—including negotiated RIMT, Spin, Battle, Cash Drop, Bad Beat, Bet-and-Muck and cash insurance—restores from its own active `game_checkpoints` row together with its complete private table state; casino rounds restore only from `casino_rounds`. There is no second snapshot-table recovery authority and no terminal-snapshot reinstallation. Boot restores and validates active new-workflow checkpoints before `refundOpenSessions()` and excludes every checkpoint-linked session from generic refunds. Clients deduplicate by room/event sequence. `room_sequences.next_sequence` and `next_table_version` permanently allocate wire `event.seq` and `tableVersion`; pruning never resets them. Recovery sets `messageSeq=next_sequence-1` and `tableVersion=max(checkpoint.tableVersion,next_table_version-1)` while retaining the committed epoch, so post-checkpoint chat/reaction/presentation events cannot be reused or create false gaps; obsolete transient payloads are suppressed. `event.tableEpoch` remains the room epoch. `TablePage.tsx` ignores duplicate/old `(tableEpoch,seq)` before `handleEvent`. A listener failure after commit does not alter committed state and is surfaced for resynchronization. Reconnect explicitly reopens the WebSocket and sends `join_table`; receipt of the resulting fresh role-safe state snapshot replaces transient presentation rather than replaying stored events. `app/src/pages/TablePage.tsx:291-310` and `:388-394` implement this reconnect/join path, while `docs/ARCHITECTURE.md:96-107` documents pushed snapshots; no table-snapshot polling path is claimed. HTTP callers retry identical operations through receipts and sequence checks. Tests inject failure at commit→install, install→event and event→reply boundaries and prove that a fresh role-safe snapshot converges after each failure. Concurrent same-revision commands produce one winner and one 409 without a lost update; a post-commit identical retry returns the stored receipt without another financial effect.

The persistence-bearing hooks covered by this plan are `onHandSave`, `onHandComplete`, `onSpinPayout`, `onTournamentPayout`, `onTournamentBust`, `onFlightSettled`, `onTournamentEnd`, `onMint`, `onBounty`, `beforeDeal`, `onSeatBusted`, `onBadBeatJackpot`, persistence listeners and coordinator save callbacks; no exhaustiveness claim extends beyond these audited paths without a new inventory. `app/server/table.js`, `index.js`, `rush-pool.js` and tournament/Battle coordinators must propagate every failure on these paths; existing catch-and-log behavior there is removed. Direct replies and listener calls occur only after commit. Fault tests cover every listed hook, Rush source-cash-out/destination-seat transfer, tournament-room changes and Battle stage/final transitions.

Ordinary cash tables retain the current graceful-close/crash-refund policy. One `hasActiveRecoveryLinkage(session)` predicate covers every checkpoint kind and casino round; any linked session uses its active recovery record and is never independently cashed out during graceful shutdown. That predicate also excludes linked sessions from generic crash refunds. On hard-crash boot, restore and validate/quarantine all active checkpoints **before** `refundOpenSessions()`. Generic refunds exclude every checkpoint-linked session, including quarantined ones. Only open sessions with neither an active checkpoint/casino round nor any new-workflow hand-start/entry receipt linkage retain the ordinary refund policy. A receipt-linked session whose expected active checkpoint is missing is quarantined, never treated as an ordinary orphan. Orphan checkpoints are quarantined for explicit audited cancellation, never resumed. Tests delete each checkpoint while retaining its hand-start receipt. Tournament settled-hand snapshots remain unchanged. Hard-crash tests cover before/during/after settlement, quarantine, orphan state and duplicate refund.

Audited quarantine cancellation never trusts corrupt stacks/cards. For a cash/RIMT seat, use the immutable hand-start receipt's validated `startingStack` for that seat and refund that amount once from the table's session escrow; this restores the current unsettled seat without reversing earlier settled wins/losses. Session escrow is reconciled after every settled hand and equals `handStartStack + pendingTopUps - pendingCashOuts`, including prior settled wins/losses/rake, so no surplus is swept to the house. A missing/contradictory hand-start receipt, escrow mismatch or residual balance blocks cancellation. Any proven escrow shortfall uses the separately funded `recovery:cash` house scope, never unscoped minting or another player's settled award. A single session-closing receipt marks the escrow terminal and prevents concurrent/duplicate refunds. For Spin, outcome_commit alone does not block quarantine cancellation. Refund each event-linked entry only when no per-entrant prize payout/refund receipt exists; refund premium only when no insurance-settlement receipt exists, preserving any already settled insurance award without clawback. Any actual prize payout blocks cohort cancellation for manual audit. For Battle, refund the event-linked entry only when no terminal prize receipt exists. Release all active house holds in the same transaction. If required receipts are missing or contradictory, cancellation is blocked and the row remains quarantined for manual audit rather than guessing. Terminal-settled workflows receive no cancellation refund. Tests cover folded contributors, prior cash winnings, insurance, settled outcomes, missing receipts and repeated cancellation.

The newest active checkpoint per room/kind is the only recoverable one. Installing its successor deletes the superseded active row in the same transaction; committed receipts and public history remain independent. Recovery requires exactly one active row per room/kind; zero rows means no active workflow, and multiple rows quarantine that exact room/kind scope without affecting other rooms. A missing, corrupt or incompatible active checkpoint fails closed and quarantines only that room/kind; recovery never selects an earlier revision. Terminal checkpoints are audit/history records and are not reinstalled. Retain terminal checkpoints and quarantined records for 30 days, then delete only those with no unresolved receipt/reference link through a bounded local maintenance call. The project documents a small-scale single-writer scope, so no capacity benchmark is a delivery prerequisite. Deterministic tests prove same-aggregate serialization, stale-revision refusal, checkpoint compaction/cleanup and zero invariant failures. An optional `game-soak.mjs` observation may record throughput, latency, database bytes and resident set size without asserting unestablished product thresholds. Retention maintenance processes at most 500 rows per call; public history is capped at 10,000 rows per room, with financial/audit receipts retained independently.

### Mandatory command identity and revisions

Every new client-originated game mutation includes its aggregate `roomId`, `expectedRevision`, `operationId` and, where configuration matters, `ruleRevision`. Event workflows additionally require `eventId`; a mutation inside a particular hand requires `handId` in addition to any enclosing `eventId`, so Battle action legitimately carries both. Between-hand room commands such as Push Seat use the room aggregate without a hand/event ID. Spin registration uses `spin-queue:<mode>:<stake>`; waiting cancellation uses `spin-registration:<registrationId>` and matched presentation uses `spin-event:<eventId>`. Every command's documentation defines which persisted aggregate supplies expectedRevision. Account, admin and configuration mutations instead use their aggregate identity (`account:<id>`, `house:<scope>`, `table:<id>`, `tournament:<id>`, `spin-rules:<mode>:<stake>` or `spin-queue:<mode>:<stake>`), that aggregate's persisted revision and the same operation/hash rules. The server binds every mutation to the authenticated account and selected options. Identical retries return committed state; a changed payload on the same operation conflicts; stale aggregates/hands/events/rules reject before charging. For RIMT, the canonical request hash covers `roomId`, `handId`, `expectedRevision`, authenticated seat and `choice`; retrying that exact payload after a lost reply returns the committed result, while any changed field on the same `operationId` returns 409 without changing state.

Financial operation IDs use the existing ledger reference identity with a unique account/operation constraint. New commands require versions; legacy compatibility behavior in `action-version.js` is not treated as sufficient for new workflows. New WebSocket mutations retain logical error codes `{type:'error',errorCode,operationId,revision,retryable}` rather than literal HTTP statuses; HTTP status assertions apply only to HTTP commands.

Server-originated timer/bot/stage mutations use a separate system-command envelope with `actorId=0`, the affected aggregate and hand/event identity, expected revision, transition name and deterministic `operationId='server:<scope>:<aggregateId>:<expectedRevision>:<transition>'`. They require no user authentication but pass the same transaction/receipt checks. Duplicate ticks and post-restart transitions return the existing system receipt without repeating effects; a later revision requires a new transition identity. Tests cover bots, blind advances, automatic showdowns, RIMT timeouts, Spin barriers and Battle transitions.

Spin registration is the pre-event exception because a match ID does not yet exist. Its identity scope is `spin-queue:<mode>:<stake>` where mode is `3max` or `6max`, and its `expectedRevision` is that exact queue's persisted revision; `ruleRevision` independently identifies the owner rules. Each `spin_register` command carries authenticated account, `mode`, `stake`, `expectedRevision`, `ruleRevision`, `insurance` and one unique `operationId`, and atomically creates at most one registration. The client orchestrates one through four independent sequential commands when multiple matches are requested; a failure stops later client requests but never rolls back earlier committed registrations. There is no partial-commit batch saga, batch receipt or batch finalization. Every response returns `registrationId`; waiting cancellation uses it with the `spin-registration:<registrationId>` aggregate, while presentation and subsequent matched play use the later event ID and new per-command operation IDs.

### Owner-funded house bank

Use an owner-capitalized play-credit bank, not implicit minting. `house_accounts` stores available funds by independent scope; `house_reservations` stores pending exposure; `house_ledger` stores signed audited movements. The invariant is checked separately for every scope:

`available + reserved = funded + settled_house_net`

`available` is spendable owner capital, `reserved` is the sum of active holds, `funded` is cumulative positive owner capitalization, and `settled_house_net` is signed house receipts/rake minus payouts already settled. All four are integer play credits. A player entry increases house net only when the entry is assigned to that scope; player-vs-player and entry-funded pools are excluded. Examples: funding 100 gives `100+0=100+0`; a receipt of 30 gives `130+0=100+30`; reserving 20 gives `110+20=100+30`; paying that 20 gives `110+0=100+10`; releasing instead gives `130+0=100+30`; cancellation of the 30 receipt gives `100+0=100+0`.

Spin uses separate prize and insurance scopes: `spin3:<stake>` / `spin6:<stake>` for prizes and `spin3-insurance:<stake>` / `spin6-insurance:<stake>` for insurance, so the active-operation hold uniqueness never conflicts. `max(prizePool)` is the maximum `stake*multiplier` across the selected mode/stake's complete configured rows. Let `E=max(prizePool)-seats*stake`. Each registration initially reserves `ceil(E/seats)` from the prize scope before its charge, protecting waiting entrants without waiting for a cohort. When the cohort fills, its transaction assigns zero-based `entrantOrder` 0 through seats−1 and reduces each hold to `floor(E/seats) + (entrantOrder < E mod seats ? 1 : 0)`; this rebalance only releases the small over-reservation and cannot fail for new exposure. Waiting cancellation releases that registration's hold. Cohort completion then commits `outcome_commit`: it selects the ticket and actual prize pool, reduces maximum exposure to actual total prize liability, and settles only insurance using that same ticket. Prize holds remain reserved throughout gameplay and are consumed/released only with actual per-place prize settlement, never at the draw. A matched event therefore has no pre-draw cancellation path; only waiting registrations may self-cancel. Quarantine cancellation is permitted after outcome_commit when no per-entrant prize payout/refund exists: entries are refunded once, premium is refunded only if that entrant has no insurance-settlement receipt, and any already settled insurance award is preserved rather than clawed back. Any actual prize payout blocks cohort cancellation for manual audit.

Battle entry-funded prizes and the separate finite bounty inventory use different scopes. Bounty inventory satisfies `capital = remaining + paid`, with no replacement after exhaustion. Underfunding rejects registration before a player charge; an already selected result is never rerolled for affordability. Unused reservations release atomically. Existing Spin mint behavior is retired by the new availability guard; owner funding and migration are audited local-admin actions, not native behavior.

There are no unscoped house-mint exceptions in the revised system. Retained owner `credit` and `set` operations are routed through `owner-issuance:USD`, `owner-issuance:PLAY`, `owner-issuance:TICKET` and `owner-issuance:GEM`: positive adjustments require available owner capitalization in that currency scope, while negative adjustments are signed `admin_adjustment` movements against the same account/scope with reason/audit identity. These operations never directly overwrite a balance without a matching house movement and are included in conservation reports. Cash Drop, slots, Prop Bet and Bad Beat Jackpot use separately capitalized house scopes with their own exposure limits and conservation reports. Existing payout paths migrate to those scopes before they are treated as funded; legacy historical credits remain historical ledger entries and are not relabelled as previously funded. Player-vs-player pots and entry-funded tournament prizes do not use house funds.

## Alternatives considered

| Alternative | Decision and trade-offs |
| --- | --- |
| Extend shared table/pot/ledger boundaries versus isolated game engines | **Extend shared boundaries.** Isolated engines duplicate evaluator, privacy, payout and recovery logic, increasing the risk of inconsistent behavior. Shared changes have higher regression cost, controlled by full variant tests and per-feature guards. |
| Narrow synchronous transactions versus a process-wide queue/outbox and coordinator cloning | **Narrow synchronous transactions.** The existing single thread/`DatabaseSync` and per-aggregate revisions supply the required serialization without a global availability bottleneck. New workflows capture only their own in-memory changes, while durable receipts and reconnect snapshots replace a second messaging system. A global queue/outbox would add delivery/recovery complexity and latency; room-only transactions without shared account/house revalidation would leave cross-aggregate races. |
| Owner-capitalized house bank versus signed house-mint ledger | **Owner-capitalized bank for this design.** It makes the selected exposure and conservation checks direct. A signed mint ledger could also be audited, but would need separate liability limits and accounting not designed here. Capitalization requires admin funding/migration and enforces exposure before player charges. |
| Explicit local rules versus leaving unobserved gameplay disabled | **Explicit local rules only where this document selects them.** This enables play without false native claims. Unsupported branded formats remain disabled/external unknown instead of receiving guessed mechanics. |
| Adaptive mobile composition versus scaling desktop compositions | **Adaptive composition.** Scaling preserves desktop art but can cause small type/targets and overlap. Adaptive controls need more component/CSS work and visual review but satisfy touch, keyboard and reflow requirements. |
| Full active-hand persistence for every cash table versus only new stateful workflows | **Only RIMT/side-workflow-active cash hands, Spin, Battle and multi-request casino rounds.** Persisting every ordinary cash hand expands migration risk. Ordinary cash without recovery linkage keeps the tested close/refund policy; every linked workflow persists the complete private table needed to resume, and one shutdown predicate covers all of them. |

## Risks and mitigations

| Risk | Mitigation and measurable gate |
| --- | --- |
| Partial wallet/hand/house/history settlement | One outer transaction; fault injection at every write; identical retry produces byte-identical committed state and totals |
| Stale command after reconnect or later hand | Mandatory identity/revision/operation IDs; wrong actor/stale hand/stale rule causes no balance change and no game-state change |
| House insufficiency or unbounded jackpot liability | Worst-case reservation before charge; safe 409 refusal; no outcome reroll; player+house+escrow reconciliation |
| Private-card/deck/ticket leakage | Role-specific allowlist projections and payload tests for actor, opponent, folded player and spectator |
| Corrupt or incompatible checkpoint | Versioned schema, card/bankroll/allocation/receipt validation, quarantine and unavailable workflow; no guessed recovery |
| Timer/restart race or duplicated presentation | Server deadlines and durable acknowledgements; restart before/during/after transition; no repeated charge, payout or fresh sound |
| SQLite contention and polling load | Synchronous outer transactions, per-aggregate revisions, bounded history and no per-second network timer; deterministic serialization/cleanup tests and no unbounded loops; optional observation-only soak is not a delivery gate |
| Shared-fixture contamination | Unique temporary data directories/accounts/ports and sequential final table captures; fixtures never target production |
| Missing/decode-failed artwork | Explicit retry/unavailable state with playable authoritative state preserved; no financial commit tied to a client asset decode |
| Mobile keyboard/safe-area occlusion | Targeted keyboard-open and standalone tests with rectangle clearance; if physical Safari/iOS testing is unavailable, report the untested coverage as a gap |

`withGameTransaction({roomIds, actorId, operationId, scope, payload}, callback)` supplies `{db, receipt, checkpoint}` to a strictly synchronous callback and returns its committed `{revision,response}`. Only the outermost call executes `BEGIN IMMEDIATE`; nested ledger/game helpers receive this context and never commit independently. Callback failures propagate. New paths emit direct events/replies only after commit and always provide latest-snapshot resynchronization; no durable outbox is introduced.

All phase-gate commands run from `app/`.

**Exact storage contract (all monetary columns use existing integer play-credit units; every statement is idempotent with `IF NOT EXISTS ` where SQLite supports it):** Phase 1 migrates only `operation_receipts`, `game_checkpoints`, the three house-bank tables, `hand_identities`, `quarantined_hand_duplicates`, `aggregate_revisions` and `room_sequences`.   operation_id TEXT NOT NULL,
  scope TEXT NOT NULL,

);

  operation_id TEXT NOT NULL,

  engine_version TEXT NOT NULL,

  updated_at TEXT NOT NULL,

);
CREATE UNIQUE INDEX IF NOT EXISTS idx_one_active_checkpoint ON game_checkpoints(room_id,kind) WHERE status='active';
CREATE INDEX IF NOT EXISTS idx_checkpoint_retention ON game_checkpoints(status,updated_at);

`aggregate_revisions` supplies initial revision 0 and monotonic queue/admin/config revisions. Every house-ledger movement has deterministic `movement_id=SHA-256(canonicalJSON([actorId,scope,operationId,movementKind,reservationIdOrEmpty,entityId,movementIndex]))`, encoded as lowercase 64-character hexadecimal. `actorId` is the initiating account/admin or 0 only for autonomous system movements, `entityId` identifies the recipient/entry/hand, and `movementIndex` disambiguates repeated kinds for that entity in one operation in deterministic sequence order. The empty-string reservation key represents no reservation. Multi-recipient Bad Beat/leaderboard payouts and admin-abort refunds therefore cannot collide, even when different actors reuse an operation ID. Retry tests assert the same movement IDs and no duplicate rows.

Every Spin registration is an independent atomic command with its own receipt, revision and response. Client-orchestrated multi-registration stops after the first rejected command; already committed registrations remain valid, and retrying any earlier identical command returns its own stored receipt without charging again. A registration starts with a unique `registration_id`, null `event_id` and `waiting` status. The same transaction charges entry/premium, reserves exposure, and matches the oldest eligible waiting rows in `(created_at,registration_id)` order only when mode, stake and rule revision agree. When the cohort reaches three or six rows, it creates one `spin_events.event_id`, links every registration through `spin_event_entrants.entrant_order`, marks them matched, and leaves every earlier receipt's immutable response unchanged. A command response returns its own registration ID plus the event ID known at that commit (null while waiting); clients poll the role-safe registration state when their cohort completes in a later command. At most four waiting/matched unsettled registrations per account/mode/stake are allowed; a fifth returns 409 before charging. Waiting cancellation refunds only that registration's entry/premium once and releases its hold. Matched registrations cannot self-cancel because cohort completion has already committed the outcome; their only recovery is ordinary play or the separately guarded admin quarantine-cancellation path. Tests fail before/during/after registration and cohort creation and verify independent retry, stable event mappings, FIFO order, cancellation and mixed success/rejection outcomes without batch finalization.

New receipts are written for every new mutation command, financial or not. Canonical JSON recursively sorts object keys, uses NFC strings, rejects undefined/nonfinite/non-safe-integer numeric inputs and array holes, and serializes without insignificant whitespace; SHA-256 over its UTF-8 bytes produces lowercase 64-character hexadecimal `request_hash`. The hash covers the authenticated actor, command, scope, identity/revisions and allowed fields; the stored response is returned byte-for-byte on an identical retry until the documented receipt compaction, after which the replay marker is returned with no effects. Financial ledger/audit rows are permanent; operation receipts are not a second permanent full-response store. Financial/game-audit receipts retain full responses for 90 days after terminal settlement, then compact to `{replayed:true}` while retaining actor/operation/scope/hash/revision; an identical later retry returns that replay marker with no financial effect instead of the expired original response. Presentation-only receipts may be deleted after 30 days when their terminal checkpoint is eligible. Released/consumed house reservations are deleted after 90 days when their permanent house-ledger movements and no active references remain. Maintenance runs at boot and every six hours in-process, at most 500 rows per call, and reports any remaining backlog to `/admin`; it never deletes active receipts/holds or blocks settlement. The enforced recovery envelope is at most 25 active resumable workflows and 1 MiB canonical JSON per checkpoint; additional new workflows return 409 before charging, and ordinary cash remains available. Tests cover the cap, oversized checkpoint rejection, retention/backlog and compacted-retry behavior. Hand history insert first claims `hand_identities` and inserts once; a repeated hand ID returns the original result. Migration creates schemas without rewriting balances and passes a second-boot test. Existing nonblank hand IDs are inserted only when unique per table; duplicate groups are copied once into `quarantined_hand_duplicates`, shown read-only in `/admin` and excluded from automatic side-effect replay. Blank hand IDs receive a new server identity on the next write and are not duplicate-grouped. Existing open sessions get no active checkpoint and retain legacy refund behavior.
